# The pathway to the ideal /analysis coach

**Written:** 2026-10-07, against commit bb912aa. **Target:** [IDEAL_PRODUCT.md](IDEAL_PRODUCT.md). **Status:** the route, element by element, with costs. Where the route was not reasonable the target changed (the section "What changes in the ideal" lists every edit, and IDEAL_PRODUCT.md carries them).

**How this was made.** Thirteen readers each took one element of the ideal and read the code against it (what exists and is reusable, what changes, what is new, cost, risks). A skeptic then re-read every "exists" claim at its cited line, grepped for code the reader had called new, listed the work the reader missed, and challenged the cost. Two planners sequenced the verified elements from different angles (value first, risk first), a cutter decided what the ideal should give up, and a judge merged them. Costs below are the skeptic's, with the reader's in brackets where they differ. The scale: S is one PR under a day, M is one or two PRs over two to four days, L is three to five PRs over one to two weeks, XL is more than two weeks or new infrastructure. One developer working with an AI coding agent, every PR green on tsc, vitest and both Playwright legs.

## The verdict

The ideal is reachable. Three sentences of it were not, and they change: cross-game pattern mining over the player's whole platform archive (there is no engine to run it), sparring built from `/play` (that page is a human-opponent client), and "any move the coach cites is evaluated before it is shown" on the server (the server has no engine). Everything else is wiring, reshaping and composition over code that already exists, which is the good news. The bad news is the size of the wiring. The thirteen elements sum to roughly 115 to 160 working days for one developer with an agent, before the overlap between them is subtracted and before anything runs in parallel. That is six to eight months to the whole ideal. The route below is ordered so that the player feels the product change in the first six weeks and the accuracy floor never moves.

Four facts about the codebase shape every estimate:

- **AnalysisImpl.tsx is 10,925 lines** with 34 components inside it, 35 useState hooks in the page component alone, and no unit test that imports it. Every client change in every element lands in it, verified by Playwright only (44 specs, two legs, nine to ten minutes each). Four elements (moment, annotations, phone, arrival) edit the same 500-line region. The route serializes client work and starts with a partial extraction so later PRs touch their own files.
- **The prompt snapshots are per attitude.** Seven follow-up snapshots and ten turn-1 snapshots regenerate on any prompt wording change. Decision 3 (one Masti) collapses them to one each. The route retires the attitudes before any element touches a prompt, so the refresh is paid once.
- **The free CI gates import the referee's symbols.** The validator dry-run (22 fixtures) and the contract fidelity smoke run on the desktop leg without an API key and break on any referee signature change. The keyed CI-4 and CI-5 gates (persona, citation, fabrication) need `ANTHROPIC_API_KEY` and a committed results JSON before a prompt or referee change ships. Every prompt-changing PR carries a manual keyed run.
- **Two deploy flags decide which code runs.** `MASTERMIND_VALIDATORS_ENABLED` and `CONTRACT_CATEGORIES` are absent from `.env.example`. The docs say both were on in production by July 2026. Every server PR must cover the flag-off branch too.

## What changes in the ideal

Each line below is an edit the skeptics forced. IDEAL_PRODUCT.md has been updated to match.

1. **Memory (cross-game).** The account gives what it can give without an engine: openings played, results by colour and time class, rating trend, the record over the last 10/25/50 games. Recurring patterns are tracked across the games reviewed here. Every review writes a digest automatically. The answer names its window ("across the 7 games you reviewed here"). A background pass over unreviewed games is an optional desktop accelerator, never the design. Why: Vercel functions cap at 60 s, the only off-box compute is a 0.1 CPU Maia box, chess.com serves no evals, Lichess serves them only for games already analysed, and a client sweep is about 60 s of CPU per game.
2. **Modes.** Sparring is built from the engine (a second, lazily armed Stockfish worker, the twinBot Elo-to-depth clamp, Maia for opponents under 1320), not from `/play`. Puzzle mode is built on the analysis board from the drill that already runs there plus the hint stages, with its coaching through the one transcript, not from the puzzle coach panel (which owns its own chat, composer and mini-board). Walkthrough is a state of the proof line, not a mode. Recap is a view of this session's lessons and drill set until memory and diagnose land.
3. **The diagnosing question.** The first build asks "show me the threat you saw" and takes the answer as a move on the board or a typed move, with Skip and "no idea" as first-class answers. The grade is deterministic (exact, partial, miss) against the engine's reply and the threat tree. The cause is derived from the grade and the truth move's features. Five library lessons. The drill set is the mistake-puzzle rows the server already returns. The graded reply is UI-authored. A free-text answer and a model classifier come later, once there are real answers to build fixtures from.
4. **The accuracy loop, bounded.** Every concrete claim is a field the app can check. A field that fails goes back to the coach once with the computed result. If it fails again the field is omitted and the unknown is said in one clause. A line the app has no evaluation for is shown as legal and unevaluated until the engine element lets the client score it. On turn 1 the loop runs per moment after each block arrives, never mid-stream.
5. **What-if timing.** Drawn with a first evaluation within two seconds and settled at the review depth after, both moves scored in one search so the difference is comparable. On follow-ups the asked moves and the engine's best are computed. Every other move the coach cites is licensed from lines already computed.
6. **Speed.** Arrival is drawn by the client from its own engine data within a second of the engine finishing. The server's contract and the model's words stream in after and never gate the first frame. A follow-up's first words come under two seconds on the served path with validation after the stream. The 60-question set is the product bar, measured by a manual keyed run with a committed results file. Speed itself has one gate: time to first token and total per follow-up, p50 and p95, plus median words.
7. **Arrival.** The scene happens when the engine finishes, from the player's side when it is known and from White's side until then. While the engine reads, the board sits at the start and Masti is reading.
8. **Annotations.** A moment's board state is tap-driven. Tapping a passage, its move, or Play puts the moment on the board with its annotation. Scroll sync is a desktop-only enhancement that yields to a playing line and to the player's own navigation. "Whose idea" is a colour named once in the strip's state row, never a label on the arrow.
9. **Phone.** The conversation is a sheet over a board whose box never changes, in two states a tap apart: at rest it shows the move's row and the composer, raised it covers the board to its bottom edge with the strip as its header. Playing a line or entering a board mode lowers it. Sending a question raises it. The board never shrinks with scroll (scroll is not input under the layout-shift rule the suite holds).
10. **Intents.** The sixteen-intent vocabulary stays as the routing table and the telemetry key. The answer shapes collapse to four grammars: a moment about one move, a moment about two moves, a no-board moment, and an acknowledgement. An intent whose fact source has not landed gets the one-move grammar plus the one-clause unknown.
11. **Opening.** The ideas for both sides are shown, not told: the master motifs the app computes (castle side, pawn breaks, piece routes, trades) drawn on the board, the book's paragraph quoted verbatim with attribution beneath. The coach's two lines name and point. A model-written plan paragraph waits for a teaching claim class.
12. **The moment.** A server-built object. Board state, verdict, evals, proof reference and actions are computed from the contract (already true today). The model fills the prose slots. Turn 1 keeps its bracket grammar as transport for one release and the server parses each refereed card into a typed moment. Structured output per field lands on follow-ups first.
13. **Perspective.** No change to the text. One reading is fixed: "every fact re-read for the other colour" means the opponent's moments become the subject. The player stays "you".

## The elements

### moment: the moment as the unit

**Today.** The computed half of a moment already exists on the server for every carded ply (`InsightContract` in [src/lib/contract/types.ts:173](../src/lib/contract/types.ts#L173): boards, verdict, evals, engine lines, the game's continuation, motifs). The server already decides which plies get a moment and in what order (the card plan). The model contributes prose in a bracket grammar that the client re-cuts with four regexes, and the length budget those regexes rely on did not hold live (147 to 222 words against 100). `callLLM` already supports JSON-schema output but only on the non-streaming path ([src/lib/llmProvider.ts:96](../src/lib/llmProvider.ts#L96)), used today by the Haiku claim parsers alone.

**The gap.** The four prose slots the prompts already describe (idea, what happens, lesson, question) and the proof reference are not fields. Every downstream consumer reads one string: the block gate, the ladder, both referees, the validators, the response and context caches, six eval scripts, 17 prompt snapshots, four e2e stubs and the card renderer.

**What exists to build on.** Turn 1 already streams whole cards as bursts, not tokens ([enforcedStream.ts:9](../src/lib/contract/enforcedStream.ts#L9)), which retires the old objection that structured output would break incremental streaming. The ladder's sentence drop is already span-based. The share excerpt already works on a text projection. A `CriticalMoment` type sits half-built in `src/lib/mastermind/criticalMoments.ts`. Line stories already produce a model-free "what happens" candidate.

**The route the skeptic chose.** Follow-ups first, behind a third `COACH_FOLLOWUP_PROMPT` mode: the model fills a moment envelope via `outputSchema` on the existing non-streaming call, the server projects it to today's prose grammar so every downstream consumer and the five other `/api/chat` callers stay byte-identical, and the client renders fields only once the schema is proven live. Turn 1 keeps the bracket grammar as transport and the server parses each refereed card into a moment, emitting a `moment` event beside the text. No streaming JSON scanner (that would be new infrastructure with no precedent in the repo) until the prose-parsed moments provably miss the two-line bar.

**Cost.** As the reader planned it (a streamed JSON document on turn 1): XL, 18 to 28 days, 10 PRs. On the skeptic's route: L, about 8 to 11 days in 5 PRs (schema module S, follow-up route behind the flag M, client renderer M, server-parsed turn-1 moments M, the stream-body provider change S).

**First PR.** A pure module, `src/lib/coach/moment.ts`: the Moment type, its JSON schema written to the structured-output rules (`additionalProperties: false` everywhere, nullable by `anyOf`, no string constraints), `momentToText()` and a lenient parser for the OpenAI fallback, with tests. No call sites, no snapshot, no e2e.

**Risks.** The two-line budget cannot be schema-enforced (the API rejects length constraints) and must be a post-check. Conversation history and the context cache must keep storing the text projection. Two output formats in flight means the response cache must be keyed by format. The 50-entry context cache has no byte bound in code (the "50 x 60 KB" figure is a plan target with no test), and storing moments beside the review doubles the entry.

### annotations: board annotations computed by the app

**Today.** The analysis board is Chessground 9.2.1, not react-chessboard. Shapes are computed in one memo ([AnalysisImpl.tsx:8687](../src/components/preview-analysis/AnalysisImpl.tsx#L8687)) that merges four reader-opted toggle arrows (engine best green, most common blue, game played orange, Maia purple, all off by default) with the gold exploration arrow. A vertical eval bar already animates with a 220 ms transition. The square-bearing facts the ideal wants (fork targets, hanging pieces, attacked squares) are already computed for every proof line and every strip move by `lineStory.ts`, and then thrown away by `captionLine`. Nothing maps a transcript moment to the board except the anchor jump and the tap handlers.

**The gap.** An annotation model (per moment: arrows and squares with a source tag, built from the game's moves, the engine's PV, story facts and chess.js attack facts, no model text), two wrapper props to show it (Chessground's `setAutoShapes` and per-square custom classes are native but unexposed), and the tap-to-board path.

**What exists to build on.** The ideal's two moment arrows are the existing `game` and `best` toggle branches, computed from the stored eval and the move list. Eleven brushes are registered, including the pale variants. Framer-motion's `useInView` is already in the bundle. `buildLinePreview` already returns the FEN for every ply of a line. A per-position annotator exists (`src/lib/positionAnnotator.ts`, 666 lines) and is not fit to reuse: 105 ms per call, reports only the single best capture, counts the attacker's own captures as defenders.

**What changes.** The wrapper gains `autoShapes` and `squareClasses` props and CSS for the custom square classes (shared site-wide by three other surfaces). `captionLine` returns the per-ply facts alongside the caption. The strip and the transcript share one annotation builder. User drawings move to the auto-shapes bucket so a Masters-tab user keeps their own arrows.

**Cost.** L [L], 8 to 11 days, 5 PRs. Four of the seven changes land in AnalysisImpl. No existing test covers the shape path, so the merge must be extracted to a pure function to be testable at all.

**First PR.** A pure `boardAnnotations.ts` that turns a position, its story facts or motif, the played move and the engine move into arrows and squares, with vitest, plus the additive facts pass-through on the caption. This proves the data is sufficient and cheap before anything touches the monolith. If a visible step is wanted first: force the best and game arrows on for a key moment's ply when its passage is tapped, about 20 lines, no new props.

**Risks.** Timings measured in this container: `buildLineStory` 89 to 119 ms per 8-ply line, `analyzeMoveAt` 27 to 146 ms per cursor move, so annotations must ride the strip's existing call rather than recompute. The board cursor has three owners today (keys, a playing line, the anchor jump) and no arbiter. Arrow labels are one or two characters at most in Chessground.

### intents: the intent router

**Today.** There is no router. Every follow-up gets one prompt, one shape, one fact pack, one budget and one action (the anchor). The six-category Haiku classifier runs only when the validators are on, sequentially before the data fetch, with no timeout and its cost dropped, and only to pick the validator timeout. `/api/classify-intent` is reachable only from a 3,549-line component that nothing mounts.

**The gap.** A pure `routeIntent()` module (rules first for actions, slash commands, move-shaped questions via the anchor's `askedSan`, walkthrough, quiz, try it, defend it, side switch, keep it short, and one Haiku call for the rest) that becomes the pipeline's category through a map, so there is still exactly one Haiku call per turn. A per-intent table (grammar, budget, fact-pack selector, allowed actions, model-call-needed). An `actions[]` response channel beside `anchor`.

**What exists to build on.** The synthetic tester already has six per-category question generators and a `--category-mix` sweep, so the intent distribution can be measured offline before any shape is written. A tablebase client (7-man, 5 s timeout) already runs on turn 1. The opening explorer and its client cache exist. The what-if fact pack is half there: the alternative's board is already rendered into the anchor block and licensed for the referee. The forced-category bypass in `routeHelpers.ts:257` is the hook for rule-routed turns.

**Cost.** L [L], 8 to 12 days, 5 PRs, for the router, the four grammars, the actions channel and the shapes whose facts exist today. What-if, compare, opening, endgame and progress each add a PR once engine, opening and memory land, and that cost sits with those elements.

**First PR.** Shadow only: `src/lib/coach/questionIntent.ts` beside the anchor resolver, returning the intent and whether a rule matched, called inside the contextId branch, logged on the existing `followup_anchor` line, echoed as `intent` beside `anchor` in both fast-path returns. No prompt, category, client or schema change. Add the classifier's 3 s abort and its cost to the telemetry in the same PR. Measure the distribution with the existing sweep, then land the category map behind a flag.

**Risks.** Two Haiku calls per turn if the router is added beside the classifier instead of replacing it. The intent-to-category map silently decides which validators fire. "Go to move 20" and "why was move 20 bad" both match the move-number regex, so action rules must run first and be conservative. A client `intentHint` may select a row in a server table and must never be interpolated into a prompt.

### engine: on-demand evaluation

**Today.** The only engine is Stockfish 17 Lite, single-threaded WASM in a browser worker. The review sweep runs depth 16 with three PVs and a warm table. The client ships the whole eval set to the server, which caches it. An asked alternative is already parsed and its board built but never evaluated: the prompt says only "the player asks about X as an alternative", the eval validator skips, the referee licenses no line, and the wrapper cannot score a chosen move at all (`go depth N` only). The server has no engine (the `stockfish.js` dependency is imported by nothing but a type file).

**The design.** Client-computed, server-verified. `UciEngine.evaluateMoves({fen, moves, depth})` uses UCI `searchmoves` with MultiPV equal to the number of moves, so the asked move and the engine's best are scored in one search at one depth. The result travels as `clientEvals` in the chat body. The route verifies structure with chess.js (FEN reachable, every move and PV legal), bounds the numbers, cross-checks against chessdb or Lichess when they hold the position, and adds the result to the existing anchor licence pool so the referee and validators treat it exactly as the review's own lines. A server engine (design B) is XL and already priced and declined in the repo.

**What exists to build on.** The `searchmoves` wrapper exists as a Node class in the openings builder. The two-engine policy (a real engine and a prober whose table is cleared) exists in the intent probe scripts. A headless runner of the shipped lite-single worker exists and is the proof harness. The client-computed, server-verified payload is already specified as `nullMoveProbes` in the intent plan. A strength-limited engine exists for sparring (`UCI_Elo` 1320 to 3190).

**Cost.** L [L], 8 to 12 days, 5 PRs: the engine primitive (S), the server contract (M), the client hook in AnalysisImpl (M), compare and quiz grading on the same primitive (M), the second-leg verify-before-show (M).

**First PR.** `evaluateMoves` alone in `uciEngine.ts`, ported from `build-eval-gaps.mjs`, with a fake-worker unit test and a headless run against the shipped worker to prove `searchmoves` plus MultiPV behave on the lite build. That proof de-risks everything after it.

**Risks.** Two live defects must be fixed on the way: the eval validator checks every claim against the played move's eval and would delete a correct what-if number, and the client never reads `askedSan`. Three eval regimes on one screen (the review's warm number, the live effect's deeper number, the what-if's cold pair) must never be subtracted across each other (the repo measured p99 disagreement of 367 cp for the same position). A single cold search at depth 16 is 1 to 3 s on a desktop and 4 to 12 s on the repo's phone model, so the first drawn line must come from a shallow partial. The score convention (White-relative, side-to-move, mover-relative all exist) must be chosen and tested, since a sign slip is a P0.

### perspective: the subject side as request state

**Today.** The side is a review-time constant baked into the contextId key, the cached context, both insight scans, the stored worst-moves section, the anchor label, the referee's pronoun map, the per-user prompt tail, the follow-up prompt's "coach the side named in USER CONTEXT", the validators' single perspective input, and eleven colour-reading sites on the client. Switching side nulls the contextId and the next message is a full flagship re-review.

**The gap is selection and addressing, not data.** Evals are White-relative everywhere, the move table already narrates both colours' flagged moves, accuracy for both sides is in the contract head, and an anchored question about an opponent's move already gets its boards, engine line and licence. What an unanchored "from Black's side" question lacks is any opponent moment in the contract or the worst-moves list, and every layer resolves "you" from the frozen colour.

**The route the skeptic chose.** Perspective is the subject side of a turn, never the addressee. The player stays "you". Under that rule the referee and the validators need no change, which is where most of the cost would have been. Perspective is per-turn request state (never in the contextId or the cached prefix). The opponent's worst moments for an unanchored subject turn are computed in the chat route from the stored eval with the helpers the anchor path already uses, and licensed through the existing anchor channel. The contract, the builder, the compact contract and its memory bound stay as they are. The reader's alternative (carrying both colours' insights at review time) was rejected: it sits on turn 1's critical path (6.2 s of CPU measured for ten plies on an 84-ply fixture), reaches eleven consumers of `contract.insights` including both turn-1 licence pools, and reopens the measured regression where the opponent's blunders became the student's lessons.

**Cost.** L [L], 7 to 9 days, 3 PRs on the lazy path (10 to 14 on the review-time path).

**First PR.** Server only: `perspective` optional on the chat schema, a prose resolver beside the anchor resolver ("from Black's side", "what was my opponent thinking", "back to my side"), the bare "move N" default following the subject, the anchor label following the subject, worst moves emitted for both colours with the subject's section picked, a per-turn opponent block for unanchored turns through the anchor licence, one override clause in the follow-up prompt, the subject restated in the turn reminder, `perspective` echoed in the response. Byte-identical for every request without the field or a perspective phrase.

**Risks.** The per-user tail ("Always analyze the game from the perspective of X playing as White") is sent uncached every turn and fights a per-turn perspective line. Fixing it touches all ten turn-1 snapshots, so it rides the attitude retirement. The four-exchange history replay carries answers in two subjects after a switch, so the subject must be restated every turn. "Your rook" slips by the model about the subject's piece are dropped by the referee until a keyed probe measures how often Haiku slips.

### accuracy: from deleting sentences to verifying claims

**Today.** The app already computes the facts before the model speaks. Two prose-shaped enforcers delete what they cannot license: a per-card referee on turn 1 (five deterministic checks over 2,130 lines of SAN, eval and keyword licensing) feeding a four-rung ladder whose floor is a template card, and a Haiku pipeline plus a sentence-level referee on follow-ups. The regenerate loop that sends a failed claim back with the expected and actual values already exists ([regenerate.ts:95](../src/lib/mastermind/validators/regenerate.ts#L95)) as a whole-answer retry. Teaching is a three-regex exemption. The chess.js relational oracle is not enabled on the follow-up path.

**The gap is shape, not machinery.** Every piece that would turn claims into checkable fields exists and is unjoined: the provider's output schema, the JSON-schema parser factory, ply-indexed line replay (in three places), the fact-id grammar, line stories, the contract focus.

**What becomes.** One pure `momentChecks` module over a fielded moment: the proof line legal by replay at its ply, the eval attached by the app from engine data it holds (a model-authored eval is a violation), annotations resolved from fact ids to squares, the two prose lines through the already-measured keyword, piece-on-square and relational checks, the lesson as a labelled teaching class with no eval, SAN or square. A field that fails is regenerated once with the computed result in the user turn, else omitted with a one-clause unknown. Once moments reach turn 1, the SAN walker (about 670 lines) and the eval pool in `refereeChecks.ts` collapse to "no SAN or eval in prose except the moment's own move", and the ladder's surgical-edit and template rungs retire on `/analysis`.

**Cost.** L [L]. The follow-up half is M, 3 PRs, 5 to 7 days. The turn-1 half is L, 4 PRs, 8 to 12 days, blocked on moment: about 110 referee tests, the fidelity dry-run fixtures, the shadow and overview referees, the arming table and the keyed gates all move.

**First PR.** Behind a new `COACH_FOLLOWUP_PROMPT=fielded` mode on the contextId path only: ask Haiku for the moment envelope via `outputSchema`, run `momentChecks` over the fields, regenerate once with a retry instruction that names the field and carries the computed result, then serialize the envelope back into today's grammar and hand that string to the unchanged referee as a second net. Nothing in AnalysisImpl, the history builder, the five other callers, the e2e mocks or the dry-run gates moves. Add a telemetry counter of field-level failures, which is the measurement the retirement PRs need.

**Risks.** "Drop, never hedge" must be pinned as a test: a failed field is regenerated once or omitted, and the only text the app adds is a one-clause statement of absence. A field regeneration is a second Haiku round trip (2 to 4 s) inside the five-second bar, so it must be one field with one result. The arming table's own rule forbids arming any new check at error until false positives are measured on a keyed run. Telemetry rows are keyed on check names and governed by a no-spans, no-FEN privacy rule.

### memory

**Today.** Nothing remembers a standing instruction: the context cache is an in-memory map (50 entries, 2 h, per warm instance), the chat route replays only the last eight messages, and the durable prefs are four Firestore user-doc fields. Cross-game data exists in pieces and none of it reaches the coach: both platform fetchers, a 12-month own-archive reader, a rating-history crawler, history aggregates over saved games, intent episode families. The chat route passes the uid as the user name, so the history matcher never matches. One "weakness profile" module is dead code. A typed per-game digest and its aggregate already exist as a dead localStorage draft (`src/lib/playerProfile.ts`).

**The gap.** A structured session-prefs channel (enum-typed fields, never free text: a client-supplied standing instruction is the exact prompt-injection hole the audit closed). A per-game digest written automatically when a review completes, stored under the account within consent, aggregated into a Progress fact pack. Engine-free facts from the platform account (openings by colour, results by time class, rating trend) for the Progress intent on day one, with the window named.

**What exists to build on.** Engine-free Progress facts already have a client fetcher and a pure summariser with 13 tests (`src/lib/performance/`), a rating trend per time control already server-fetched for `/plan`, and the improvement-strategy category already routed with a user-history citation validator (48 tests) that checks three claim types.

**Cost.** XL as the reader planned it (with the background analyser): 15 to 25 days, 11 PRs. L with the analyser and the depth preference cut: about 10 to 12 days. Hidden costs the reader missed: six `storeAnalysisContext` sites in the 2,672-line review route for the user-name fix, a prompt branch for a Progress answer (today's shape allows 45 words for a non-move question), a referee allowance (its move pool is this game only), a validated route with a size cap and a limited read for the digest subcollection, erasure in `deleteUserData.ts` (8 tests), and a consent toggle across the eight-file saved-pref path plus privacy copy for an audience that includes minors.

**First PR.** Session prefs without storage: an enum-typed `sessionPrefs` object (side, explained plies) on the chat schema, passed through the request-body builder, rendered as one standing line at the top of the uncached suffix, held in client state and resent on every turn. Depth is cut from this PR: the word budget and token cap live in the stable prompt and the turn reminder, so a depth setting is a prompt parameter with snapshot re-pins.

**Risks.** Regime drift: digests from depth-12 background runs, depth-16 reviews and Lichess cloud evals are different instruments and must not be mixed into one accuracy trend. Lichess serves evals as an `analysis` array on the NDJSON path, not as PGN comments, so the parser is of that array. Consent off by default means Progress is empty for most accounts until adoption. No platform-API stubs exist in the e2e helpers, so any new fetch on `/analysis` reaches third-party APIs in CI unless stubbed.

### diagnose: the question, the cause, the lesson, the homework

**Today.** The only coach-asks surface is the prompt's optional "Your turn:" paragraph, rendered as a note with no state behind it. The player's reply is an ordinary follow-up, nothing grades it, no cause is named, the lesson is model-written each turn, and the drill hand-off pulls Lichess puzzles by theme from Neo4j rather than this game's positions.

**What exists to build on, more than the reader saw.** The server already computes per-game drop positions (at least 150 cp) with the FEN, the move played, the correct move, evals and motifs on both response paths, and the client discards them ([enhanced-analysis/route.ts:1209](../src/app/api/enhanced-analysis/route.ts#L1209)). The drill mode already grades a played move on the main board (a one-puzzle `DrillState` started with `handlePromoteToBoard` saves and restores ply and orientation). Position i+1's root line is the opponent's best reply, free, so the truth for "what was the threat" needs no new search. An in-transcript puzzle grader exists twice. The forced-category bypass skips the Haiku classifier for a known turn kind.

**The first build (per the edit above).** A pure `src/lib/diagnose/` with `decisiveMoment.ts` (the player's max-drop ply with the sentinel and depth guards copied from `selectInsights`) and `gradeAnswer.ts` (a UCI or SAN answer against the engine's reply, the threat tree's captures and checks, and the relational hanging and pin facts, returning exact, partial or miss, the truth, and the cause derived from it). Then the client only: a synthetic coach turn with the question and Answer on board, Type, Skip, the answer taken through a one-puzzle drill state, graded on the client, and a synthetic graded reply with the library lesson. No route, prompt or snapshot change.

**Cost.** As the reader planned it (Haiku classifier, 15 to 18 authored lessons, telemetry table, board-tap wrapper change): L, 12 to 16 days, 6 PRs. As the first build: M, 2 to 3 PRs, 4 to 6 days.

**Risks.** The engine truth is only concrete at tactical moments (the threat tree finds captures of at least 200 cp, checks, mates). At a positional decisive moment there is no move to grade, so the question is asked only where a concrete threat exists and otherwise asks for the plan. Drill puzzles cut from a player's own game are often quiet, so the set must filter to forcing lines or single-move finds and fall back to the theme store, saying so. A typed answer is user content and must never enter the tracking tables.

### modes: one page, many stages

**Today.** `/analysis` already runs three unnamed modes on one Chessground board that is created once and never remounts: review, Masters-explore with the takeover preview, and a drill mode that remembers the ply to return to. ### speed, cost and the bar

**Today.** The measured latencies are the August gate runs: turn-1 time to first token p50 1.3 to 1.7 s, first card 15 to 20 s, total p50 20 s and p95 59 s, about 10.5 s per extra card, and five cards do not fit Vercel's 60 s. The follow-up is non-streamed JSON behind an optional Haiku classifier and a validator pipeline, with a May localhost series of 24 follow-ups at p50 5.4 s and p95 7.6 s, already over the five-second bar, and time to first token equal to total because nothing streams. Cost is measured: about $0.07 per Sonnet review, $0.0035 to $0.0045 per Haiku follow-up on a cache hit. Production latency is unobservable: no log drain, no timing on the chat response.

**What closes the gap.** Instrumentation first (time to first token, elapsed, prep and retry count on the chat response and the structured log, copied from the puzzle-chat route, plus the same fields in the synthetic tester). Then the contract builder's pre-stream CPU off the turn-1 critical path: measured here at 1.7 s for two insights and 6.0 s for ten insights on an 84-ply game, attributed to the threat tree (about 30%), the line stories (about 30%) and the per-ply FEN replays (18%). Then a streamed follow-up with post-stream correction (the puzzle-chat route already does exactly this), zero validator retries on follow-ups (a one-token change: the route hard-codes one), a 60-word and about 350-token budget with the turn-1 review no longer replayed as the first assistant message, and per-intent tier selection.

**Cost.** L [L], 10 to 14 days, 6 PRs for the latency work. The 60-question set and the jury calibration belong to the intents and accuracy elements and to a process outside code (three human raters).

**First PR.** Two byte-neutral pieces: the instrumentation, and one game walk replacing the per-ply `getFenAtHalfMove` replays in the builder (output-identical, pinned by the rollback drill and 41 contract tests, removes about a second of pre-stream CPU on long games).

**Risks.** The validators-on follow-up branch cannot stream as built (classifier, data fetch, then generate, validate, regenerate before the first token). First words under two seconds is a decision to move validation after the stream, not a tuning target. Streaming and then deleting a sentence the player has read is the hole the ideal forbids, so the correction must be field-scoped. Anthropic's prompt cache idles out after five minutes, so on a low-traffic site most calls pay the cache write. Haiku's output rate bounds "complete under five seconds" at the token cap, not only the word budget.
